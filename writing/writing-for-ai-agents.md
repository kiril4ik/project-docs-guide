# Writing for AI Agents

> **What:** How to write and organize docs so LLMs and AI coding agents read them correctly and act on them reliably, without making them worse for humans.
> **Read when:** your team uses AI assistants, or your docs feed a chatbot, search or RAG system.

## TL;DR

- **What's good for humans is good for agents:** clear structure, explicit statements, consistent terms, working examples.
- Agents have **no tribal knowledge**. Anything implied must be **written down**.
- Agents navigate by **entry files, links and search**. Predictable paths and index files matter more than ever.
- Make every page **self-contained enough** to be understood when retrieved alone (RAG chunks).
- Use **stable IDs** (rules, requirements, ADRs) so agents can cite and cross-reference precisely.

---

## How agents consume docs

| Mechanism | Implication for your docs |
|---|---|
| Load an **instruction file** at start (`AGENTS.md`, `CLAUDE.md`) | Keep it short; make it the map to everything else |
| **Follow links** from file to file | Relative links, descriptive link text, indexes in each folder |
| **Search** (grep, semantic search) | Use the words people would search for; consistent terms; IDs |
| **Chunking** (RAG): split pages by heading | Each section understandable alone; headings that name the topic |
| **Limited context window** | Concise pages; summaries first; no giant files mixing topics |
| **Literal interpretation** | Explicit rules ("always", "never"); no sarcasm or ambiguity |

## Rules

### 1. Be explicit, not implicit

| ❌ Implicit | ✅ Explicit |
|---|---|
| "Use the usual approach for money." | "Store money as integer minor units (cents) in `*_cents` columns. Never use floats." |
| "Don't touch the legacy stuff." | "Do not modify files in `src/Legacy/`. They are frozen until migration RFC-0031 completes." |
| "Run the tests." | "Run `composer test`. All tests must pass before committing." |

### 2. Make every section stand alone

A retrieved chunk may be seen **without** the rest of the page.

- ❌ "As mentioned above, it requires approval."
- ✅ "Refunds over €500 require finance manager approval (BR-PAY-04)."

Repeat the **subject** in headings: `## Refund approval rules`, not `## Rules`.

### 3. Structure over prose

- Use headings, lists and tables. Agents extract structured content more reliably than long paragraphs.
- Put **key facts in predictable places**: front matter, TL;DR, tables.
- One topic per file. Mixed files produce mixed answers.

### 4. Consistent terminology and stable IDs

- One term per concept, defined in the [glossary](../foundations/glossary.md). Agents treat synonyms as different things.
- IDs for rules, requirements and decisions: `BR-PAY-04`, `FR-PAY-012`, `ADR-0012`.
- Reference IDs in code comments and tests, so agents can trace rule → code → test with a single search.

### 5. Show correct and incorrect examples

Agents learn patterns from examples. Pair each convention with ✅ and ❌ code from *this* codebase.

### 6. Mark status and authority

- Front matter `status: deprecated` plus a visible banner, so agents don't follow outdated docs.
- Mark the canonical source: "Canonical: this page. Other mentions link here."
- Put dead docs in an `archive/` folder and tell agents to ignore it in `AGENTS.md`.

### 7. Give a map

In `AGENTS.md` or the docs index, include a short **docs map**:

```markdown
## Where to find things
| Need | Location |
|---|---|
| Business rules | docs/requirements/rules/ (IDs BR-*) |
| Architecture decisions | docs/architecture/decisions/ (ADR-*) |
| API contract | api/openapi.yaml (source of truth) |
| Local setup | docs/getting-started/README.md |
| Do NOT use | docs/archive/ (historical only) |
```

### 8. State boundaries and procedures as commands

```markdown
## Rules for AI agents
- Never edit applied migrations in `database/migrations/`; create a new one.
- Never commit `.env` or files in `storage/`.
- Before claiming a task is done, run `composer test && composer lint`.
- When changing an API endpoint, update `api/openapi.yaml` in the same change.
```

## Agents as doc writers

Agents can draft docs well, provided you give them structure:

| Give the agent | So that |
|---|---|
| This guide's [decision-guide](../choosing-structure/decision-guide.md) and [templates](../templates/README.md) | Output fits your structure |
| The style guide | Consistent tone and formatting |
| The rule: "Write working notes to `.agents/`, final docs to `docs/` only after review" | Docs root stays curated |
| A requirement to mark output: `> Draft generated by AI on <date>; needs review` | Reviewers know what to check |
| An instruction to cite sources (files, ADRs) for claims | Easier fact-checking |

Review checklist for agent-written docs:

- [ ] Facts verified against code and specs, with no invented flags, endpoints or config keys
- [ ] No placeholder text left from templates
- [ ] Links resolve
- [ ] Doesn't duplicate an existing doc
- [ ] Correct location per the organizing rules

## Formats beyond Markdown for agents

| Format | Use |
|---|---|
| `AGENTS.md` / `CLAUDE.md` | Repo instructions ([ai-agent-docs](../doc-types/ai-agent-docs.md)) |
| `llms.txt` | Curated index of a public docs site |
| OpenAPI / JSON Schema | Machine-precise contracts; agents read them well |
| Front matter | Machine-readable metadata (status, owner, IDs) |
| Markdown tables | Rules, mappings, parameters: easy to parse |
