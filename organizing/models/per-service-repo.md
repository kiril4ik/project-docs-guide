# Model: Per-Service Repos + Central Portal

> **What:** In a multi-repo (polyrepo) architecture, each service or repo keeps its own docs, and a central portal, catalog or index repo ties them together.
> **Read when:** your organization has many repositories (microservices, many teams), and nobody can find anything across them.

## TL;DR

- Each repo uses the **same standard layout** for its own docs (README, `docs/`, API spec, runbooks).
- A **central place** aggregates or indexes them: a developer portal (such as Backstage), a docs site that pulls repos in, or a simple index repo.
- **Organization-wide** docs (architecture landscape, standards, onboarding, glossary) live in a dedicated **handbook / engineering docs repo**.
- The hard part is **consistency**. Enforce it with a repo template and CI checks.

---

## What it looks like

```
Organization
├── handbook/                        central repo: org-wide docs
│   ├── README.md
│   ├── architecture/                landscape, cross-service flows, org ADRs
│   ├── standards/                   coding, API, security standards
│   ├── onboarding/
│   ├── glossary.md
│   └── services.md                  service catalog (or generated by the portal)
│
├── billing-api/                     each service repo, same layout
│   ├── README.md
│   ├── catalog-info.yaml            portal metadata (e.g. Backstage)
│   ├── openapi.yaml
│   └── docs/
│       ├── index.md
│       ├── architecture.md
│       ├── decisions/
│       └── runbooks/
│
├── catalog-api/
│   └── ... same layout ...
│
└── developer-portal                 renders all of the above in one place
```

## Standard per-repo layout (make it a repo template)

| Path | Required | Purpose |
|---|---|---|
| `README.md` | ✅ | Purpose, owner, quick start, links |
| `docs/index.md` | ✅ | Docs landing for the portal |
| `docs/architecture.md` | ✅ | Service internals, dependencies |
| `docs/runbooks/` | Production services | On-call procedures |
| `docs/decisions/` | When decisions are made | Service-level ADRs |
| API spec (`openapi.yaml`, `.proto`, `asyncapi.yaml`) | If it has an API | Reference source |
| Portal metadata file | If using a portal | Owner, lifecycle, dependencies, links |

## Aggregation options

| Option | Effort | Notes |
|---|---|---|
| **Index page** in the handbook repo listing all repos + links | Low | Manual, OK for <20 repos |
| **Docs site** that pulls repos at build time (git submodules, a multirepo plugin, CI sync) | Medium | One search across all docs |
| **Developer portal** (Backstage TechDocs, Port, Cortex, etc.) | High | Catalog, ownership, docs, API specs in one UI |
| **Generated catalog** from repo metadata | Medium | Always current service list |

## Pros and cons

| ✅ Pros | ❌ Cons |
|---|---|
| Docs stay with code and team | Cross-service knowledge needs a separate home |
| Strong ownership | Inconsistent layouts without enforcement |
| Scales to hundreds of services | Portal setup and maintenance cost |
| Service docs versioned with service | Search across repos needs tooling |

## Best for

- Polyrepo microservice organizations, roughly 10+ repos.
- Platform engineering teams that build an internal developer portal.

## Avoid when

- Few repos (<5). A central index page in each README is enough.
- A monorepo. Use [co-located](co-located.md) + central `docs/` instead.

## How it fails (and the fix)

| Symptom | Fix |
|---|---|
| Each repo's docs look different | Repo template + CI lint ("docs/index.md must exist") |
| Org-level decisions scattered across service repos | Org ADRs in handbook repo, service ADRs in service repos |
| Portal shows stale/abandoned services | Lifecycle field in metadata; periodic ownership review |
